# Geometry built in C# is SRID 0 unless you say otherwise, and the columns are 4326

Every geometry column in this schema is **SRID 4326** (WGS84, lon/lat). The migrations set
it explicitly — `ST_SetSRID(ST_MakeLine(ST_MakePoint(lon, lat)), 4326)` in
[20260523120007_PostGIS.cs](../../backend/Infrastructure/Migrations/20260523120007_PostGIS.cs)
and its siblings — and geometry read back from the database carries it.

**Geometry constructed in C# does not.** NetTopologySuite's default factory produces
SRID **0**, and nothing in the type system objects. On develop there is exactly one site
that gets this right explicitly:

```csharp
// backend/Core/Repositories/TrailRepository.cs:74
Geometry.DefaultFactory.WithSRID(4326).CreatePoint(new Coordinate(lon, lat))
```

Everywhere else a `Point` or `LineString` is built for a query or a write, the `.WithSRID(4326)`
is load-bearing and easy to omit. The consequences differ by backend, which is what makes
it slippery:

- **PostGIS** refuses a mixed-SRID operation outright, or silently computes a distance in
  degrees rather than what you expected.
- **SpatiaLite** (the test provider) enforces the column's SRID on insert, so the same
  omission shows up as a *test* failure with a geometry error, not as a wrong answer.

So an SRID slip can be green on one path and red on the other, in either direction.

## Order of coordinates

`new Coordinate(x, y)` is **(longitude, latitude)** — X is longitude. The wire format the
clients speak is `{ latitude, longitude }` objects. The swap is silent and puts things in
the Gulf of Guinea; [docs/spatial-data.md](../spatial-data.md) is the reference for that
boundary and for which repository methods do the conversion.
